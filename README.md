# stock-recommendation · A 股股票推荐系统

> **与 `quantitative` 量化纸盘项目完全独立。** 两者不共享模型、不共享结论。
> 量化项目继续做量化；本系统只做「推荐」。
>
> 状态：**阶段 0（归档地基）+ 阶段 1（确定性筛选层）+ 本地网页工作台已落地**。

---

## 这个系统在解决什么

一句话：**把「翻 5,000 只股票」变成「看 20 只候选 + 每只的理由」。**

价值不在预测准确率，而在**结构化、可解释、不漏关键风控**。

### 三条不可动摇的判断

1. **数据分四层，只有两层能进打分权重。**

   | 层 | 内容 | 能否回补历史 | 能否进权重 |
   | --- | --- | --- | --- |
   | **T0 已就绪** | 日线 / 涨幅 / 基本面 / 上市日期 | — | ✅ |
   | **T1 可回补** | 题材归因、龙虎榜、交易所两融、公告 | ✅ | ✅ |
   | **T2 仅当日快照** | 板块排名、分钟资金流、北向、涨停梯队 | ❌ **必须自建归档** | 建档前不可 |
   | **T3 不可回测** | 新闻文本、研报预期、社媒情绪 | ❌ 结构性不可 | ⛔ **永不** |

2. **「拿不到准确的消息数据」不是要解决的问题，是要绕开的问题。**
   不预测消息，改测**市场对消息的反应**（价格 / 成交量 / 资金流 / 涨停开板）——
   客观、完整、可归档、可回测。消息真假最终一定在成交与资金上留痕。

3. **不能回测的数据永远不能进权重。**（**可证伪性**约束，不是数据质量问题。）
   新闻没有历史时点快照 ⇒ 永远无法回测 ⇒ 你无法知道它有没有用 ⇒ 进权重就是纯噪声。
   ⇒ 消息类数据**只做风控闸门 + 解释层**。

另外：「预期兑现」用**状态机**建模，**不用 NLP**。题材生命周期（启动 / 发酵 / 高潮 / 退潮）
每一阶段都有可观测的数量特征（tag 频次、涨停家数、换手极值、涨停开板率、板块资金净流出）。

---

## 为什么先做归档

**T2 类数据只有当日快照，没有 `date` 参数。晚一天上线，就永久少一天数据。**

所以归档层必须**先于任何因子和模型**上线。本仓库当前的阶段 0 就是在做这件事。

### 本地网页工作台（推荐使用方式）


每次启动网页服务后，第一次打开页面会自动按 `SYNC_SOURCE_REGISTRY` 同步全部已启用数据源：
行情、题材、龙虎榜、官方两融、板块快照，以及 BaoStock 估值/财务，并重新生成推荐；页面
会显示每个源的阶段进度、警告和本地归档覆盖。同一个服务进程里的页面交互不会重复抓取。
T1 数据会自动读取各归档表的最后成功日期，从下一交易日一直追平到本地行情最近一个已收盘交易日；
收盘前如果行情源已经出现盘中日期，推荐会自动退回上一交易日，避免把收盘后数据误判为缺失；收盘后
再同步即可继续追平当天。BaoStock
首次建立当前全市场快照，之后只新增交易日估值，在新报告期出现时更新财务，不需要手动设置
“最近几天”。需要立即重试时，可以点击「再次同步全部数据」。板块快照属于 T2，只能保存
当前日，无法历史回补。

BaoStock 财务首次同步默认使用 4 个独立连接并发；可在 `config/default.toml` 的
`[fundamentals].workers` 调低到 1（网络受限时）或按实际环境调整。默认会同步最近 5 个
已公告财报期，并保存资产负债表、现金流量表字段，用于计算营收同比、利润增速加速度、
连续增长期数、财务安全分和现金流质量。PE(TTM)由项目内当日收盘价和 BaoStock 的
EPS(TTM)计算并落盘，同时比较行业内 PE；PB/PS/PCF 暂不以替代值填充，也不参与评分。

每次生成推荐还会自动写入 `data/reports/forward/`：推荐快照（JSON）、运行汇总
`journal.jsonl`、逐次验证 `evaluation.csv` 和按 1/5/20 个交易日汇总的
`evaluation_summary.csv`。行情推进到新的交易日后，下一次启动或同步会自动更新验证结果；
网页的「验证记录」页会区分“已完成验证”和“持有期尚未走完”，不会把未成熟样本当成亏损。

项目根目录的 `一键检查并启动.cmd` 是可随目录搬运的便携启动入口；它会检查 Python、`.venv`
和 Streamlit，缺少环境时自动调用初始化脚本。Windows 资源管理器中也可以直接双击它。

推荐清单中的每只股票都展示综合分、实际权重覆盖、行业、板块/题材、评分拆解和人类可读理由。
推荐计算只读取当前目录的 `data/market`、`data/reference`、`data/archive.duckdb`；网络
请求只在启动自动同步或点击同步时发生，结果会先写回本地再参与推荐。

推荐卡片还会基于已有日线生成一次性的「今日操作参考」：参考价、分批买入区间、回落价、
不追价上限、逻辑失效价、两个参考目标价和短期兑现状态。这些字段只用于解释推荐后的
操作思路，不参与综合评分、不维护真实持仓，也不需要分钟数据；分钟级早盘 / 尾盘规律
不在本项目当前数据范围内。操作价格和理由会一起写入 `data/reports/forward/` 的推荐
快照，后续可与 1/5/20 个交易日的实际走势对照。

节前窗口另有市场级资金安排提示：交易所休市日前的最后两个交易日会提示卖出资金的转出时点。
该提示依据交易所公布的休市安排，当前覆盖 2024-09 至 2026 年；新年度官方日历发布后需要更新
`src/recommend/calendar_risk.py`。日历出处见[上交所 2024 安排](https://www.sse.com.cn/disclosure/announcement/general/c/c_20231226_5733939.shtml)、
[上交所 2025 安排](https://big5.sse.com.cn/site/cht/www.sse.com.cn/disclosure/announcement/general/c/c_20241223_10767108.shtml)、
[上交所 2026 安排及调整](https://www.sse.com.cn/disclosure/announcement/general/c/c_20251222_10802507.shtml)、
[2026 中秋/国庆调整](https://www.sse.com.cn/disclosure/announcement/general/c/c_20260915_10832273.shtml)。
它不会把节前下跌当成已验证规律，也不改变筛选、个股排序或价格计划。

行业来自 `data/reference/industry_master.csv` 的本地快照，同时用于行业景气 / 行业内龙头分位。
需要刷新时运行 `scripts\refresh_industry.py`；刷新失败不会覆盖已有本地快照。PE(TTM)、EPS、
ROE、毛利率和利润同比来自项目内 `archive.duckdb`，推荐计算不会运行时直连网络。

### 免费数据链路的实施顺序

当前按「影响大、免费、容易验证」排序：

1. **官方两融优先**：`backfill margin` 默认逐交易日抓上交所 JSON + 深交所 XLSX，
   支持断点续跑；数据不依赖东财，接口缺失的字段保持空值。
2. **龙虎榜主备链路**：东财主源先取完整买卖金额；主源失败才切新浪，新浪备用源只
   提供上榜事件和说明，不把缺失金额填成 0。
3. **本地日线补充因子**：实现波动率、60 日最大回撤、20 日成交额方向压力，以及
   「低位 + 20/60 日均线确认」预设。它们先用于筛选和解释，**不修改默认评分权重**。
4. **前向纸盘**：新增逻辑必须从产生推荐之日起等待实际后续 20 个交易日，再与当时
   冻结的 spec 对账；没有满 20 日之前不宣称有效。
5. **BaoStock 基本面**：同步最近 5 个已公告财报期，并用本地收盘价 + EPS(TTM)计算当前
   PE(TTM)及行业内相对估值；同时补充营收增长、利润/EPS 增速加速度、连续增长、流动性、
   杠杆、利息保障和经营现金流质量。归档按 `pub_date` 截断，避免财报发布日期晚于推荐日
   时产生前视偏差。PB/PS/PCF 暂不以替代值填充。首次同步会并发逐股票请求，后续同一交易日
   会幂等跳过。
6. **沪深交易所公司公告**：日常拉取交易所公告目录，按每个交易所单独保存同步游标，并重抓
   最近 5 天以修正迟到/漏抓数据；断档会从上次成功日期继续补。明确标题由本地关键词规则免费
   分类；含糊标题每次最多 25 条进入待分类队列，由现有 16:00 Codex Plus `gpt-6-luna max`
   任务只根据公告标题做分类，不下载 PDF、不调用 API、不购买额外 credits。分类结果只作候选
   股票的公告提示，不改变筛选条件、分数、排序或操作价格；队列处理失败会保留待下次重试。

板块资金流仍放在最后：当前 `push2` 端点在本网络环境不可达，而且这类数据没有可靠
历史回补；在建立可验证归档前不进入评分。

所有自动同步入口都共用 `src/recommend/sync.py` 中的 `SYNC_SOURCE_REGISTRY`。以后新增源时，
只需注册一个 `SyncSource` runner；网页启动同步、手动同步和 `recommend sync-all` 会自动执行，
并在前端显示独立进度和失败详情。

## 阶段 1：确定性筛选层（无 LLM）

流程：`spec（条件）→ 因子宽表 → 过滤 → 透明加权 → 候选表 + 理由`。

### 1. 「低位」只做筛选，924以来收益进入动量排序 —— 由代码**机械保证**

位置类因子（`close_position_*` / `dist_to_52w_high`）既不能做 `sort`，
也不能出现在排序权重里。写进去会**直接报错**，不是靠自觉：

* `screen/spec.py` 的 `ALLOWED_SORTS` 不含位置因子；
* `rank/score.py` 的 `_validate_weights` 遇到位置因子键就 `raise RankWeightError`。

理由：低位可能是价值（错杀），也可能是价值陷阱（基本面恶化）。它适合把 5,000 只缩到 200 只，
**不适合**决定买谁。当前 `momentum` 类还加入了相对等权市场的 20/60 日收益，和 `risk` 类的
波动/回撤方向分；各成员先分别做横截面分位，再在类别内等权平均。行业展示字段本身不加权，
但行业景气分和行业内龙头分位会进入 `industry` 权重。

### 2. 缺失值有四条铁律

| 情形 | 正确做法 | 为什么不能偷懒 |
| --- | --- | --- |
| 上市不足 250 个交易日 | `close_position_250` = **NaN** | 拿 30 天的区间冒充一年的位置 |
| 题材归档当天为空 | 热度 = **NaN** | 填 0 会让「没回补」伪装成「全市场都没热度」，条件静默失效 |
| 龙虎榜归档为空 | `lhb_*` = **NaN** | 填 0 等于宣称"没上过榜" |
| 两融归档为空 | `margin_rz_chg_20` = **NaN** | 填 0 等于宣称融资余额没有变化 |

对应地，**筛选时 NaN 一律判不通过，并且单独计数**（`<字段>:缺失`），
与「不在区间」分开显示。如果并成一个数字，归档断档时你会以为条件生效了。

### 3. 漏斗账目必须对得上

每次筛选都给出完整剔除日志，且满足：

```
universe − Σ剔除 − 被 limit 截断 = 保留
```

`limit` 截断必须**单独披露**（"未显示 ≠ 未通过"）—— 否则「命中 25 只」会被读成
"恰好 25 只满足条件"，而实际可能是 438 只满足、只给你看 25 只。

### 4. 排序不用 ML，用透明加权

权重写在 `config/default.toml` 的 `[rank]`，是**政策参数、不是拟合结果**。
每个成员因子先转成**横截面分位秩**（对极端值免疫），按类别加权；
类别整列缺失时权重在剩余类别间**重新归一**，并披露 `score_coverage`。

默认权重如下，合计 100%：

| 类别 | 权重 | 主要量化内容 |
| --- | ---: | --- |
| 行业 | 20% | 行业景气、行业内市值龙头 |
| 增长 | 18% | 净利润/EPS/营收同比、增速加速度、连续增长 |
| 财务质量 | 15% | ROE、毛利率、现金流/净利润、负债安全 |
| 估值 | 15% | PE(TTM)、相对行业 PE |
| 动量 | 15% | 20/60 日收益、924 以来收益、相对市场收益、量比 |
| 风险 | 8% | 波动率、最大回撤、下行波动 |
| 流动性 | 5% | 20 日成交额 |
| 题材 / 资金 | 4% | 题材热度、龙虎榜、两融和主力净额（数据可用时） |

⚠️ `main_net_inflow` 只对当日进入题材归因名单的股票有值 ⇒ 它的分位是在**很小的样本**上算的。
这不是 bug，但要知道它比其它因子噪声更大。

### 5. 每条推荐必须带「数据时点」

报告固定输出 `## 数据时点` 段。没有它，读者无法判断这是不是拿陈旧数据当今天。
同时报告会显式说明「名称（含 ST 标记）取当前状态，本表不用于历史回看」——
用今天的名称回看三个月前，会含未来信息。

### 6. spec 是白名单枚举

`Spec.from_dict` 遇到未知字段**报错而不是忽略**。因为阶段 2 的 LLM 会**编**字段名：
忽略 ⇒ 条件静默变少 ⇒ 结果变多，而使用者以为条件生效了。
这是全系统唯一一处"宁可不干活也不能猜"的地方。

支持写法（区间统一成 `(min, max)`）：

```json
{"themes": ["算力"], "ret_ytd": [-0.2, null], "volume_trend_20": ">1.5", "limit": 20}
{"filters": {"close_position_250": {"max": 0.3}}, "limit": 20}
```

### 7. ⚠️ 日期必须在拼进 SQL 前**整体**校验

`as_of` 将来来自自然语言翻译层，会一路拼进 duckdb 查询。`market._iso` 用 `fullmatch`
校验**整个字符串**，而不是先 `[:10]` 再校验 —— 后者会把
`2024-09-24' or '1'='1` 的前 10 个字符截成合法的 `2024-09-24`，**校验通过而注入部分被保留**，
等于没校验。这个 bug 真出现过，被 `tests/test_market.py` 抓到。

## 前向纸盘：唯一能验证 T2 的办法

数据分三档，**能做的检验完全不同**：

| 档 | 例子 | 能否回补 | 能做的检验 |
| :--- | :--- | :--- | :--- |
| T0/T1 | 日线、题材归因、龙虎榜、两融 | ✅ | 历史回测、逐点重放 |
| T2 | 板块排名 + 板块资金流、分钟资金流、北向分钟、涨停梯队 | ❌ **只有当日快照** | **只能从今天起逐日留证** |
| T3 | 新闻文本、研报一致预期、社媒情绪 | ❌ 结构性不可回测 | 永不进权重 |

⇒ T2 意味着「按今天的题材热度 / 板块资金流选股是否有效」**没有任何历史样本**。
唯一的证据来源是：**从今天起，每个交易日冻结一次当时的输入与输出**，若干交易日后
拿实际走势对账。这件事**无法补做** —— 晚一天开始，就永久少一天样本。

### CLI 归档任务（可选）

```bash
.venv/Scripts/python.exe -m recommend.cli daily-job      # 或 scripts/daily_job.cmd
```

一次跑齐注册表内的数据源和留证步骤，**各步互不拖累**，适合命令行使用或需要单独补跑前向纸盘时运行：

| 步骤 | 档 | 今天没跑成会怎样 |
| :--- | :--- | :--- |
| 行情推进 | T0/T1 | 明天增量窗口自动补回 |
| 题材归因 | T1 | 明天从归档最后一天之后续抓 |
| 沪深交易所公告目录 | T1 | 按独立同步游标自动补齐缺口，最近 5 天重抓修正 |
| T2 快照 | **T2** | **永久缺失，补不回来** |
| 筛选 + 留证 | —— | 不能补造为当时真实发出的推荐；历史重算需单独标注 |

### 缺失同步与每日运行

- **T0/T1 可追补**：日线下次同步会从最后成功日期向前追平；题材、龙虎榜和交易所两融可按
  日期回补。历史重算可以用于研究，但如果当时没有冻结候选名单、数据时点和生成时间，
  不能算作真实的前向推荐样本。
- **T2 不可追补**：板块排名、板块资金流等只有当日快照；错过当天就永久缺失，必须在运行记录里
  显示缺口，不能用后来的数据补成历史值。T3 新闻、研报和社媒也不进入历史评分或前向验证。
- Codex 本地项目定时任务在**工作日 16:00（北京时间）**运行 `scripts/daily_job.cmd`。工作日
  **09:30–15:30** 日常同步会暂停，网页只读本地最近一个完整交易日；16:00 任务开始后，
  若当天收盘行情尚未确认，则仍可追补行情和 T1，但跳过推荐生成与前向留证。
- 定时任务随后读取 `data/reports/announcements/pending.json` 中待处理的公告标题，输出分类 JSON，
  再通过 `apply-announcement-classifications` 写入 DuckDB；有分类结果时重算报告，不重复生成
  前向留证。仅使用该定时任务已有的 Plus `gpt-6-luna max` 配额，不配置 API key 或额外付费
  额度。Plus 配额不可用时队列会保留，下一次任务续处理。
- 收盘任务每次汇报各数据源状态。T1 缺口后续继续追补；T2 缺口不回填；错过的推荐日不事后补造。
- GitHub Actions 版定时任务在工作日北京时间 **18:00** 运行（GitHub cron 使用 UTC，配置为
  10:00 UTC）。上交所交易公开信息文件在闭市后发送，但没有承诺具体分钟；交易所两融公开
  信息按规则于下一交易日开市前发布。18:00 为盘后数据留出缓冲，同时保留当日 T2 快照；
  若当晚两融等 T1 数据尚未到位，近 5 个交易日的空结果会在后续同步中重试。它从最新完整状态继续运行；首次启动才从 Git LFS 拉取日线和 DuckDB，之后不
  重复下载这些大文件。每次保留一份最新完整状态 artifact，并以 Actions Cache 保存近 7 天的
  完整恢复点。artifact 约 154 MiB；七份缓存约 1.06 GiB，使用与 artifact 分开的缓存额度。
  Cache 可能按 GitHub 的不活跃/容量规则提前淘汰，因此七天历史点属于尽力保留；最新状态仍由
  单份 artifact 维护，冷启动时还可从 Git LFS 重建初始状态。
- 需要回退时，在 Actions 对应运行摘要中复制 `Cache key`，再手动运行该 workflow 并填写
  `restore_snapshot_key`。它会恢复并提升该完整快照为最新状态，不执行当日同步；下一次定时运行
  再从恢复后的状态继续。
- GitHub Actions 仅运行本地确定性规则，不调用 Codex Plus。含糊标题会留在待分类队列；现有
  Codex Plus 定时任务仍在本机运行，生成的分类不会自动同步到 GitHub。Actions 负责定时同步和
  保存报告/状态。每日同步还会把最新候选清单与前向验证摘要发布到
  [GitHub Pages 公共只读页面](https://alex-wang-88.github.io/stock-recommendation/)；网页只发布
  当前展示候选和验证摘要，不公开归档数据库、公告待分类队列或日线原始文件。该页面是静态只读展示，
  本地 Streamlit 工作台仍用于完整交互和手动同步。

同步会把每一步的失败和缺失明确显示出来，不会用一句“完成”掩盖部分数据没有更新。

### 三条机械保证

1. **spec 指纹不含 `as_of`**（`forward.spec_fingerprint`）。前向测试要的是「同一个 spec
   连续跑 N 天」；把每天都变的 `as_of` 算进指纹，等于每天都换了一个 spec，无法归组。
2. **留证要存当时的 `close`**。只存代码不够：日后复权基准变化会让"用现在的行情回算
   当时的推荐"失真。
3. **留证要存剔除日志与 notes**。没有它，「那天只选出 2 只」事后分不清是条件太严、
   还是某个因子整列缺失把池子清零了 —— 整个样本作废。

### ⚠️ 同一个 as-of 重跑，候选可能变

实测：2026-09-18 先跑了一次（题材归档还停在 09-17 ⇒ 题材因子全缺失），补抓题材后
再跑，**前 25 名换了 4 只**（题材权重 0.30）。这不是 bug，是"输入变了"。

所以：

* 单次记录文件 `<as-of>__<hash>.json` 会被**最后一次运行覆盖**，`journal.jsonl`
  保留每一行 —— 「同一天跑过几次」这件事本身也留痕。
* 前向测试要的是"在**能实际下单的那个时点**看到的名单"，所以云端定时任务放在收盘后并
  为上游数据留出缓冲（18:00，北京时间），而不是盘前。
* 想复盘"数据没补齐时会选出什么"，靠 `notes` 与 `rejections` 复现条件，
  而不是靠候选名单本身。

### 对账

```bash
.venv/Scripts/python.exe -m recommend.cli forward-report
```

按 1 / 5 / 20 个交易日算候选组与全市场等权的后续收益差。

⚠️ **持有期没走完的记录不会按 0% 计入**（那会把"还不可测"伪装成"没涨没跌"），
而是从 `measured` 列里排除。样本天数少时这些差额基本是噪声 —— **要看方向是否一致，
不要看点估计大小**（理由见「配对日频检验」一节：本样本 80% 功效下的最小可分辨
年度化差额约 10–14 pp，而这里要判的是 2–4 pp）。

### 行情增量的两个陷阱

1. **快照接口不带日期** —— 日期只能从**行情源自身**取（`resolve_quote_date` 读报价里的
   时间戳），**绝不用系统时间**。否则周五的行情会被写成周六，而周六在归档里
   "看起来是个交易日"，之后所有按交易日对齐的逻辑全部错位。
2. **前复权序列会整体平移** —— 除权除息会让整条序列重算。所以增量追加必须做
   **重叠比对**：新拉的与已存日重叠的收盘价对不上 ⇒ 该标的发生了公司行动，整窗重拉。
   漏掉这一步会在除权日造出一个**虚假大跌** —— 而「低位」筛选恰好专挑这种票。
   实测（2026-09-16 → 09-18）全市场有 **42 只**触发修复，这不是理论担忧。

⚠️ `AdvanceResult` 里 `rows`（写入行数，含重叠窗口）与 `new_rows`（真正新增）
是两个数，相差近 10 倍（全市场 15 根重叠 ≈ 8 万行，真正新增只有 1 万行）。
简报时不要混用。

## 归档层的关键设计

### 1. 终态必须分开记：`OK` / `EMPTY` / `REJECTED` / `FAILED`

非交易日返回空是**正常**的（`EMPTY`）；接口失效返回空是**故障**（`FAILED`）；
响应回来了但**是别人的那一天**是第三种情况（`REJECTED`，见下方第 6 条）。
混在一起，归档覆盖率就没法信了 —— 你会分不清"市场休市"和"我们的任务坏了"。
每次运行都写进 `archive_runs`，四种状态分开统计。

### 2. 幂等 + 断点续跑

默认跳过已归档的日期（`--force` 覆盖）。回补可以随时中断、随时重跑，不会产生重复行。

### 3. 整日替换 vs 逐键 upsert（**按数据源区别对待**）

* **题材归因用整日替换**（先删该日再插）。因为同花顺接口**一次返回全量、无分页**
  ⇒「抓取成功」就等于「拿到当天完整名单」，整日替换不会误删；
  而上游若修正名单（变短），残留行会污染题材阶段判定。
* **龙虎榜用逐键 upsert**。因为它有 `page_size` 分页上限，**部分抓取是可能的**
  ⇒ **宁可残留，不可误删**。

### 4. 金额一律存「元」

不在归档层做万 / 亿换算。换算是展示层的事，归档层不做有损转换。

### 5. 缺列报错，不静默补空

`store.upsert` 遇到缺列会 `raise`。静默补空会把「数据源改了字段名」
伪装成「这些值本来就缺失」—— 这是最难查的一类 bug。

---

### 6. ⚠️ 必须校验「响应到底属于哪一天」（回退快照陷阱）

**这是本仓库踩过的最大一个坑，也是归档层最重要的一条规则。**

同花顺 `getharden` 对**它没有数据的日期**不报错、不返空 —— 而是**静默返回它自己最新的那份快照**。
后果：**38 个法定休市日被当成交易日写进了归档**，全部持有同一套 79 只股票。

实测证据（污染识别）：

| 检查 | 真实交易日 | 回退快照 |
| --- | --- | --- |
| 行数 | 46–731，逐日变化 | **恒为 79** |
| `change_pct` 填充率 | **100%**（42218/42218 行） | **0%**（3081/3081 行全 NULL） |
| 股票集合指纹 | 每日唯一 | **39 天共用一个指纹** |

**两道独立校验，在本数据集上均零误报：**

1. **行级 `date` 回显**必须等于请求日期。请求 `2024-10-01`（休市）时回显的是接口当天的最新数据日
   ⇒ 直接露馅。归档表因此保留 `source_date` 列，事后可审计。
2. **必须带行情字段**。真实交易日 100% 有、回退响应 0% 有。

任一单独使用都有漏洞（只查回显会漏掉"当日占位"载荷；只查行情需要逐源标定），所以**两道都跑**。

**配套设计**：把"上游回退"记为**独立的终态 `REJECTED`**，与 `EMPTY`（真的没有）、
`FAILED`（报错）分开。它其实是"这一天没有数据"的**证据** —— 只是上游用"给你别人的快照"
而不是"给你空"来表达。用 `recommend quality` 可随时自查。

## 东财风控：实测结论（重要）

**东财的风控是「端点 + 频率」共同触发，不是单纯封 IP。**

实测证据：在**同一秒内**，`push2his /api/qt/stock/fflow/daykline/get` 成功返回 120 条，
而 `push2his /api/qt/stock/kline/get`、`push2 /api/qt/clist/get` 被 `RemoteDisconnected` 掐断。

⇒ **判据**：一个业务端点失败时，**先跑对照端点**（`cli probe`）：

| 对照端点 | 业务端点 | 结论 |
| --- | --- | --- |
| ✅ | ❌ | **端点或参数问题**，不是被封。别加冷却，去检查 `secid` / `fields` 编码 |
| ❌ | ❌ | 网络或 IP 层面确实不可用，降低频率后重试 |

本仓库已内置：串行请求 + 最小间隔 + 随机抖动 + 会话复用。
批量任务把 `config/default.toml` 的 `min_interval_seconds` 调大更稳。

**另外**：行情类数据优先用通达信（mootdx）/ 腾讯（不封 IP），东财只用于它独有的数据中心接口。

### 2026-09-19 复测：`push2` 是**端点不可达**，不只是代理

本机同时配了 `HTTP(S)_PROXY=127.0.0.1:61579`。实测组：

| 请求方式 | 目标 | 结果 |
| --- | --- | --- |
| 走代理（默认） | `push2.eastmoney.com/api/qt/clist/get` | ❌ `ProxyError: RemoteDisconnected` |
| `trust_env=False`（**直连**） | 同上 | ❌ `ConnectionError: RemoteDisconnected` |
| 走代理 | 东财 `datacenter-web`（对照端点） | ✅ 有时通、有时不通 |

⇒ **两种方式都失败**，所以不能归因于代理：该端点在当前网络环境下确实不可达。
`fetch` 走代理自然没问题这件事，**只对腾讯成立**（`qt.gtimg.cn` / `web.ifzq.gtimg.cn` 稳）。

**后果**：在 `push2` 不可达的运行中，T2 板块快照可能采不到；如果当天没有成功落盘，
这类数据确实无法事后回补，必须让它在简报里显形。重复运行时若本地已经有该日快照，
任务会先检查本地记录并直接跳过，不再把后续网络探测失败误报成数据缺失。

⇒ 若要让 T2 真的攒起来，需要换源（例如按板块成分股**等权合成**板块日线），
或在网络层解决 `push2` 的可达性。**在研究结论出来之前，不要用板块快照做任何判断。**

## 边界（写死在设计里）

1. **推荐结果不可反哺量化模型。** 会把不可证伪的输入灌进量化项目。
2. **T2 在建档完成前只能「前进」，不能「回测」。** 不要在 T2 数据上做任何「历史表现」结论。
3. **「低位」只做筛选条件，不做排序加分。** 低位可能是价值，也可能是价值陷阱——
   让它**缩小范围**，但别让它**决定买谁**。
4. **LLM 只能出现在「自然语言 → 筛选条件」的翻译层**，且条件必须是**白名单枚举**
   （未知字段报错，不猜测）。LLM 不参与选股与排序。
5. **排序不用 ML。** 推荐场景样本量只有几十~几百，ML 必然过拟合；用透明加权，
   每条推荐都要能列出因子贡献。
